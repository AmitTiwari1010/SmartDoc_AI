SmartDocs AI
Complete Implementation Guide — RAG + MCP Knowledge Assistant
Version 1.0 | Practical build plan for a portfolio/interview-ready project
Goal: build a manageable but genuine GenAI application that demonstrates document ingestion, retrieval-augmented generation, vector search, MCP tools, tool calling, FastAPI, and React.
1. Executive Overview
SmartDocs AI is a document knowledge assistant. A user uploads PDF documents, the system indexes their content, and the user can ask questions. RAG retrieves relevant passages before the LLM generates an answer. An MCP server exposes document operations as standardized tools that an AI client can invoke when the request is an operation rather than a pure knowledge question.
The project is intentionally scoped so that every major component can be understood and explained in an interview. It is not intended to be a production enterprise platform in version 1.
2. Problem Statement
Normal LLMs can answer general questions but may not know the contents of a user's private documents. Sending entire documents with every request is inefficient and may exceed context limits. SmartDocs AI addresses this by indexing documents once, retrieving only relevant chunks for each question, and grounding the answer in those chunks.
A second problem is tool integration. A knowledge retrieval pipeline does not by itself provide a standardized interface for actions such as listing documents or retrieving document metadata. MCP is used to expose these capabilities through an MCP server.

4.2 Knowledge Base
List indexed documents.
Show filename, page count, chunk count, file size, and upload time.
Delete a document and its vector records.
Keep source/page metadata for citations.
4.3 RAG Chat
User submits a question.
Question is embedded using the same embedding space used for documents.
Vector search retrieves top-K relevant chunks.
Retrieved text and metadata are assembled into a context.
The LLM receives the question plus context.
The answer is returned with source references.
If evidence is insufficient, the assistant should say it cannot find the answer in the indexed documents rather than inventing facts.

6. RAG Pipeline — Detailed
6.1 Ingestion Pipeline
PDF ↓PyMuPDF ↓Page text + page metadata ↓Chunking ↓Embedding model ↓ChromaDB ├── vector ├── chunk text └── metadata {document, page, chunk_id}
6.2 Query Pipeline
User question ↓Question embedding ↓Chroma similarity search ↓Top-K chunks ↓Context builder ↓System prompt + context + question ↓LLM ↓Answer + source metadata
6.3 Why chunking?
Large documents should not be passed wholesale to the model for every question. Chunking makes retrieval more precise and keeps the prompt manageable. Start with a token-aware or character-based splitter and test values rather than treating a particular chunk size as universally correct. A practical initial experiment is roughly 500–800 tokens with 50–100 tokens of overlap.
6.4 Embeddings
An embedding converts text into a numerical vector representing semantic information. A user question and a relevant document chunk can therefore be close in vector space even when they do not share exact keywords.
6.5 Vector Search
For a question vector, Chroma retrieves the nearest stored vectors. The first version can use top-K retrieval, for example K=4. Tune K later based on answer quality and context size.
6.6 Grounding Prompt
You are SmartDocs AI.Answer using only the supplied document context.If the context does not contain enough evidence, say so.CONTEXT:{retrieved_chunks}QUESTION:{user_question}
7. MCP — Detailed Concept
MCP stands for Model Context Protocol. In this project, the MCP server is not the LLM and is not the vector database. It is a standardized interface through which an AI client can discover and invoke capabilities exposed by the server.
AI application / host        │        ▼    MCP Client        │        ▼    MCP Server      /   |        /    |     list   info  search   │      │      │   └──────┴──────┘       SQLite / Chroma
Tools in this project
list_documents: read-only metadata lookup.
get_document_info: read-only details for a named document.
search_documents: semantic/metadata-oriented discovery of documents.
Keep all version-1 tools read-only. This reduces security risk and keeps the project easy to explain. Later versions can add controlled actions only after authentication and authorization are designed.
8. RAG vs MCP
RAG:Question → retrieve relevant knowledge → provide context → LLM answerMCP:AI needs capability → discover tool → invoke MCP tool → receive result → LLM answer
RAG is about grounding generation with relevant information. MCP is about a standardized way to expose external tools/resources to AI applications. They are complementary, not competing technologies.

15. Error Handling
Reject non-PDF files in version 1.
Reject empty/corrupt PDFs with a useful message.
Handle documents with no extractable text.
Prevent duplicate document indexing unless explicitly replacing the existing file.
Return a clear error when the LLM provider is unavailable.
Return a clear message when no relevant chunks are found.
Never expose API keys in frontend code.
Use timeouts around external API calls.
Log server-side errors without logging sensitive document contents.
16. Security Basics
Keep secrets in .env and never commit .env.
Use .env.example with placeholder names.
Validate upload type and size.
Sanitize filenames.
Restrict file paths to the upload directory.
Keep MCP tools read-only in version 1.
Validate tool arguments server-side.
Treat document text as untrusted input because documents can contain prompt-injection instructions.
Do not let retrieved text override system-level safety or application rules.
If authentication is added later, authorize every document/tool operation.
17. RAG Quality and Evaluation
A working demo is not automatically a good RAG system. Test it deliberately.
Create 15–30 questions whose answers are explicitly present in your documents.
Create 5–10 questions whose answers are not present.
Check whether retrieved chunks contain the correct evidence.
Check whether the final answer stays grounded in the retrieved context.
Record source correctness and answer correctness separately.
Experiment with K, chunk size, overlap, and embedding model.
A simple evaluation sheet can contain: question, expected document, expected page, retrieved documents, retrieved page, answer correctness, and groundedness.
18. Interview Explanation
30-second version
SmartDocs AI is a document knowledge assistant built with React, FastAPI, Python, RAG, ChromaDB, and MCP. Users upload PDFs which are parsed, chunked, embedded, and stored in a vector database. For questions, the system retrieves relevant chunks and gives them to an LLM as context. I also built an MCP server exposing document operations such as listing documents and retrieving document metadata, allowing the AI application to use standardized tools.
Why RAG?
Because the model should answer from private or user-provided documents without retraining the model. Retrieval supplies only relevant evidence at query time.
Why MCP?
Because RAG solves knowledge retrieval, while MCP provides a standardized interface for exposing tools and external capabilities to AI applications.
Why Chroma?
It is simple for local development and makes the vector-search pipeline easy to understand. A production version could move to a managed or server-based vector store.
Why FastAPI?
It provides a lightweight Python API layer, request validation through Pydantic, and easy integration with the Python AI ecosystem.
Why keep MCP tools read-only?
It keeps the first version safe and easy to reason about. Write operations require stronger authorization, validation, audit logging, and failure handling.

24. First Implementation Task
Start with a tiny RAG proof-of-concept before React or MCP. Create one PDF, extract its text, split it into chunks, embed the chunks, store them in Chroma, ask one question, print the top four retrieved chunks, and only then connect the LLM. This makes every later layer much easier to understand and debug.
